# Contributing to Zynthera

Thank you for wanting to help. This page explains how to set up, what a good change looks like, and how to send it.

## Before you start

- **Small fixes** (a bug, a typo, a clearer error message): open a pull request directly.
- **Larger changes** (a new feature, a change to the database schema, the API or the PC lifecycle): open an issue first and describe what you want to do. It avoids work that cannot be merged.
- **Security problems:** do not open a public issue. Contact the maintainer privately through the links in the README's Author section.

## Setting up

Follow the README:

- [Quick start](README.md#quick-start) if you already have the tools.
- [Local setup, step by step](README.md#local-setup-step-by-step) otherwise.

For most work you do not need real virtual machines. [Mock mode](README.md#mock-mode-running-without-virtual-machines) runs the whole product against fake PCs and needs only Docker, Go and Node.js.

## Where things are

| You want to change | Look in |
|---|---|
| A page or a component | `web/src/app`, `web/src/components` |
| An API endpoint | `internal/api/httpapi` |
| Which actions a PC allows in which state | `internal/api/vms` (pure rules, table-tested) |
| How a PC changes state | `internal/api/vmsvc` and `internal/api/jobs` |
| Host choice and capacity | `internal/api/scheduler` |
| What happens on the VM host | `internal/agent` |
| The database schema | `db/migrations` (then `make generate`) |
| A SQL query | `db/queries` (then `make generate`) |
| The OS image | `images/` |

`PROJECT_SPEC.md` is the specification. `docs/DECISIONS.md` lists every place the code departs from it, with the reason.

## Rules for a change

1. **Tests come with the change.** New logic has tests in the same pull request. A bug fix has a test that fails without the fix.
2. **Everything passes before you send it:**

   ```bash
   make lint
   make test
   make test-e2e     # needs mock mode and the app running, see the README
   ```

3. **Keep it boring and readable.** Someone with modest experience should be able to maintain it. Prefer a few clear lines over a clever one. Comments explain why, not what.
4. **Follow what is there.**
   - Go: standard layout, `log/slog`, errors wrapped with context, `context.Context` on every call that does I/O.
   - TypeScript: strict mode, no `any`. API types live in `web/src/lib/api/types.ts` and must match the Go response structs.
   - JSON uses `snake_case`. Timestamps are RFC 3339 in UTC.
   - Colors, radii and fonts come from the tokens in `web/src/app/globals.css`. Do not add one-off values.
5. **A departure from the specification is written down.** Add an entry to `docs/DECISIONS.md` with one or two sentences of reasoning.
6. **Say what you could not verify.** If a change needs KVM, root or a real server and you could not test it there, say so in the pull request.

## Security rules that must never be broken

These are the reason the platform can give strangers root on a virtual machine.

- Host commands are built as an argument list (`internal/agent/run`). Never pass a string to a shell.
- Text typed by a user never becomes part of a file path, a libvirt name or a command argument. Those use identifiers generated by the system.
- cloud-init YAML and libvirt XML are produced by serializers from structs, never by pasting values into text.
- Every `/api/vms/:id/...` route checks ownership, and answers `404` for a PC that belongs to someone else.
- Never log passwords, tokens, cookies, cloud-init contents or URLs that carry a token.

`docs/SECURITY_REVIEW.md` has the full list.

## Database changes

```bash
make migrate-new name=add_something     # creates the .up.sql and .down.sql files
# write both files, then:
make migrate
make generate                           # regenerates the typed Go code
```

- Every migration has a working `down` file.
- Never edit a migration that has already been merged. Add a new one.

## Commits and pull requests

- One logical change per commit, with a message that says what changed and why in plain words.
- Keep a pull request focused on one thing. Unrelated cleanups belong in their own pull request.
- In the pull request, describe what you changed, how you tested it, and anything a reviewer should look at closely.
